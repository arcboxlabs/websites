## Start Here

```bash
abctl doctor
```

`doctor` checks the daemon socket, the System VM, the Docker API proxy, the DNS resolver, the network bridge with its VM member, the container subnet route, and the privileged helper. Most problems below show up as a specific failure there.

<Accordions type="single">
  <Accordion title="Containers won't start" id="containers-wont-start">
    **Check the daemon:**

    ```bash
    abctl daemon status
    abctl daemon start
    ```

    **Check the Docker socket symlink:**

    ```bash
    ls -la /var/run/docker.sock
    ```

    It should point at `~/.arcbox/run/docker.sock`. If it is missing or broken, the [helper](./helper) is not installed or not reachable — `abctl doctor` says which.

    **Read the logs:**

    ```bash
    abctl logs -f              # daemon
    abctl logs -c dockerd -f   # guest dockerd
    ```
  </Accordion>

  <Accordion title='Cannot connect to Docker ("Cannot connect to the Docker daemon")' id="cannot-connect">
    <Steps>
      <Step>
        Confirm the daemon is up: `abctl daemon status`
      </Step>
      <Step>
        Check your context: `docker context ls`. ArcBox's context is named `arcbox`. Activate it with `abctl docker enable`.
      </Step>
      <Step>
        Check `DOCKER_HOST` is not overriding the context: `echo $DOCKER_HOST`. Unset it, or point it at `unix://$HOME/.arcbox/run/docker.sock`.
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="Slow filesystem performance" id="slow-fs">
    Bind-mount metadata performance improved substantially in 1.31 — update first.

    - Check whether antivirus or endpoint-security software is intercepting file operations on the mounted path.
    - For write-heavy state like a database, use a named volume instead of a bind mount. See [Volumes](./volumes#bind-mounts-vs-volumes).
    - For very large trees where latency dominates, work on a path inside the guest rather than across the share.
  </Accordion>

  <Accordion title="A container cannot reach the internet" id="no-internet">
    <Steps>
      <Step>
        Check host connectivity first.
      </Step>
      <Step>
        Run `abctl doctor` and look at the container-route check. If a VPN is active, see [VPN Compatibility](./vpn-compatibility) — ArcBox adapts to route changes without a restart.
      </Step>
      <Step>
        If the route check passes but traffic is still blocked, the VPN may be filtering packets independently of the routing table. Check its local-network and packet-filter settings.
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="Cannot resolve .arcbox.local hostnames" id="dns">
    <Steps>
      <Step>
        Check the resolver: `abctl dns status`, or `cat /etc/resolver/arcbox.local`
      </Step>
      <Step>
        Reinstall it if missing: `abctl dns install`
      </Step>
      <Step>
        Flush the macOS DNS cache:

        ```bash
        sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
        ```
      </Step>
      <Step>
        Remember the port: a container's hostname resolves to its address inside the container network, so use the port the service listens on — not the published host port. See [Domains](./domains).
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="High memory usage" id="memory">
    Guest memory is not returned to macOS while the VM runs — this is expected on both hypervisor backends today. See [Efficiency](./efficiency#memory).

    - `abctl top` or the **Activity** pane shows where memory is going.
    - Stopping containers frees memory inside the guest for the next container, not back to the host.
    - Stopping the runtime is what returns it.

    If idle CPU is high rather than memory, update — 1.30.1 fixed a reclaim loop that burned CPU on an idle VM.
  </Accordion>

  <Accordion title="Publishing a port fails" id="ports">
    Port publishing runs unprivileged, so host ports below 1024 cannot be bound. Use a high port, or reach the container directly at `<name>.arcbox.local` on its own port.
  </Accordion>

  <Accordion title="Sandbox operations fail with FAILED_PRECONDITION" id="sandbox-precondition">
    [Sandboxes](./sandbox) need nested virtualization: the Virtualization.framework backend on Apple Silicon M3 or newer, on macOS 15+.

    Check and switch the backend:

    ```bash
    abctl system backend      # print current
    abctl system backend vz   # switch (restarts the System VM)
    ```
  </Accordion>

  <Accordion title="Helper authorization failed" id="helper-auth">
    <Steps>
      <Step>
        Open **System Settings → General → Login Items & Extensions**
      </Step>
      <Step>
        Enable the ArcBox helper
      </Step>
      <Step>
        Restart ArcBox Desktop
      </Step>
    </Steps>

    Confirm with `abctl doctor` — the helper check reports both reachability and version.

    <Callout type="warn">
      On managed devices, your IT administrator may need to approve the helper via MDM.
    </Callout>
  </Accordion>

  <Accordion title="App crashes or misbehaves" id="crashes">
    Work outward from the app before touching any data:

    <Steps>
      <Step>
        Quit ArcBox Desktop and relaunch it.

        Note what quitting does by default: it stops the daemon and everything it runs, and restores your previous Docker context. Keeping the daemon alive across a quit needs both **Keep running when app is quit** and **Show in menu bar** enabled — and even then, choosing Quit explicitly still shuts it down.
      </Step>
      <Step>
        **Settings → General → Troubleshooting → Export Diagnostic Report…** collects logs and system state for an issue report.
      </Step>
      <Step>
        Check whether the daemon is the actual problem rather than the app: `abctl doctor`, then `abctl logs -f`. If `abctl` works and only the window is broken, it is an app bug — please [file it](./known-issues#reporting-issues).
      </Step>
      <Step>
        Restart the runtime: `abctl daemon stop && abctl daemon start`. This stops running containers but touches no data.
      </Step>
    </Steps>

    <Callout type="error">
      **Settings → Storage → Danger Zone → Reset Docker Data** is not a fix for app crashes. It only prunes Docker state — every container, image, volume, and network, with no undo — and resets nothing about the app, its preferences, or the helper. Reach for it only when you have diagnosed corrupt Docker data specifically.
    </Callout>
  </Accordion>
</Accordions>

## Filing an Issue

Include the `abctl doctor` output, `abctl version`, your macOS version, and a diagnostic report. See [Known Issues](./known-issues#reporting-issues).
