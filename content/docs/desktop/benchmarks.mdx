## Test Environment

All benchmarks run on Apple Silicon hardware (M3 Max, 36 GB RAM, macOS 15). Numbers represent the median of multiple runs with warm caches unless otherwise noted.

## Container Startup

10,000 container starts using `alpine:latest`:

| Metric | ArcBox | Docker Desktop | Speedup |
|--------|--------|----------------|---------|
| Cold start (mean) | 312ms | 1,247ms | **4.0x** |
| Cold start (p99) | 580ms | 2,100ms | **3.6x** |
| Warm start (mean) | 89ms | 487ms | **5.5x** |
| Warm start (p99) | 145ms | 820ms | **5.7x** |

### Where the Difference Comes From

1. **Lighter hypervisor** — Virtualization.framework adds ~100ms overhead vs ~400ms for Docker Desktop's VM
2. **Optimized kernel** — stripped-down guest kernel with minimal module loading
3. **Smart caching** — pre-warmed filesystem snapshots eliminate redundant work
4. **Apple Silicon native** — no translation layer, direct hardware access

## Sandbox Start

Sandboxes are Firecracker microVMs with their own kernels, so "start" has two very different paths: a cold create boots a fresh kernel, while a snapshot restore resumes an already-booted memory image. Measured on an M5 Max (macOS 26), 1 vCPU / 512 MiB sandboxes, serial iterations against a warm daemon, timed from the API call:

| Metric | p50 | p90 |
|--------|-----|-----|
| Restore RPC (warm slot) | **81 ms** | 86 ms |
| Restore → first command output | **144 ms** | 153 ms |
| Cold create → first command output | 1.19 s | 1.20 s |
| Command in a running sandbox | 14 ms | 16 ms |

For reference, hosted sandbox services publish cold-start figures around 150 ms for the equivalent resume-from-snapshot operation. ArcBox does it locally — under nested virtualization — with the restore call completing in 81 ms.

### Where the Speed Comes From

1. **Snapshot resume, not boot** — restore maps the memory image lazily; the `LoadSnapshot` call itself takes ~3 ms
2. **Pre-warmed slots** — after a snapshot's first restore, a jailed Firecracker process with the snapshot staged waits in a pool; the next restore claims it and goes straight to resume
3. **Network-invariant snapshots** — every sandbox boots the identical internal network identity, and each TAP's external identity is applied host-side by an eBPF program, so a restored clone needs zero in-guest reconfiguration
4. **Event-driven readiness** — READY fires on an actual vsock dial-out from the in-VM agent the moment it accepts executions, not on a poll

Sandbox numbers come from the `sandbox_coldstart` end-to-end probe in the arcbox repository (`tests/e2e/tests/sandbox_coldstart.rs`); readiness is taken from the gRPC events stream subscribed before the first create.

## File I/O

Sequential read/write throughput using `fio` with a 1 GB test file:

| Operation | ArcBox | Docker Desktop | Native |
|-----------|--------|----------------|--------|
| Sequential read | 4.2 GB/s | 2.8 GB/s | 4.5 GB/s |
| Sequential write | 3.8 GB/s | 2.1 GB/s | 4.1 GB/s |
| Random 4K read | 95K IOPS | 62K IOPS | 105K IOPS |
| Random 4K write | 88K IOPS | 54K IOPS | 98K IOPS |

ArcBox achieves >90% of native filesystem performance for most workloads.

## Memory Usage

| State | ArcBox | Docker Desktop |
|-------|--------|----------------|
| Idle (no containers) | 130 MB | 220 MB |
| 1 container (nginx) | 180 MB | 310 MB |
| 10 containers | 420 MB | 850 MB |
| 50 containers | 1.2 GB | 2.8 GB |

ArcBox returns memory to the host as containers stop. Docker Desktop retains allocated memory until the VM is restarted.

## Network Throughput

`iperf3` between host and container:

| Metric | ArcBox | Docker Desktop |
|--------|--------|----------------|
| TCP throughput | 52 Gbps | 44 Gbps |
| UDP throughput | 48 Gbps | 38 Gbps |
| Latency (ping) | 0.15ms | 0.4ms |

## Methodology

All benchmarks are reproducible. Source code and scripts are available at [github.com/arcboxd/arcbox-benchmarks](https://github.com/arcboxd/arcbox-benchmarks).

Results vary by hardware. Run the benchmark suite on your own machine for numbers specific to your setup.
