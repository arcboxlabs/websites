ArcBox Desktop bundles two command-line tools: a standard `docker` CLI and `abctl`, the ArcBox runtime CLI. Both talk to the same daemon as the GUI, so state stays in sync in every direction.

<Callout type="info">
  `abctl` is the CLI's name. A compatibility shim named `arcbox` still forwards to it, but it is deprecated — use `abctl` in new scripts.
</Callout>

## Docker CLI

The Desktop app ships `docker`, `docker-buildx`, and `docker-compose` inside its bundle, and the [privileged helper](./helper) symlinks them into `/usr/local/bin`. There is nothing to download.

```bash
abctl docker enable   # create the "arcbox" context and make it the default
```

<Callout type="info">
  `abctl docker setup` downloads those tools into `~/.arcbox` instead. It exists for CLI-only installs — Desktop users do not need it.
</Callout>

`enable` creates a Docker context named `arcbox` and sets it as the current one, so every `docker` command targets ArcBox:

```bash
docker run -d -p 8080:80 nginx
docker compose up -d
docker build -t my-app .
docker logs -f my-container
```

`abctl docker status` reports the integration state, and `abctl docker disable` restores whichever context was default before.

<Callout type="info">
  The Desktop app can switch the context for you. **Settings → System → Switch Docker & Kubernetes context automatically** is on by default.
</Callout>

## Shell Integration

`abctl setup install` puts `abctl` on your `PATH` and installs completions for `abctl` and `docker`:

```bash
abctl setup install     # PATH + completions + shell profile line
abctl setup status      # check what is installed
abctl setup uninstall   # undo it
```

It writes `~/.arcbox/shell/init.<shell>` and appends a `source` line to `~/.zprofile`, `~/.bash_profile`, or `~/.config/fish/config.fish`.

To place the completions yourself instead, write them somewhere your shell already looks:

<Tabs items={['zsh', 'bash', 'fish']}>
  <Tab>
    ```bash
    mkdir -p ~/.zfunc
    abctl setup completions --shell zsh > ~/.zfunc/_abctl
    ```

    `~/.zfunc` must be on your `fpath` before `compinit` runs — add `fpath=(~/.zfunc $fpath)` to `~/.zshrc` if it is not.
  </Tab>
  <Tab>
    ```bash
    completion_dir="$(brew --prefix)/etc/bash_completion.d"
    mkdir -p "$completion_dir"
    abctl setup completions --shell bash > "$completion_dir/abctl"
    ```

    This requires Homebrew's `bash-completion@2`. On Apple Silicon the prefix is `/opt/homebrew`, not `/usr/local` — use `brew --prefix` rather than hardcoding it. Without `bash-completion`, source the file from `~/.bash_profile` directly.
  </Tab>
  <Tab>
    ```bash
    mkdir -p ~/.config/fish/completions
    abctl setup completions --shell fish > ~/.config/fish/completions/abctl.fish
    ```
  </Tab>
</Tabs>

## Command reference

<Tabs items={['Runtime', 'Machines', 'Sandboxes', 'Kubernetes', 'Diagnostics']}>
  <Tab>
    ```bash
    abctl daemon start        # start the ArcBox daemon
    abctl daemon stop         # stop the daemon and all workloads
    abctl daemon status       # show daemon state

    abctl system backend      # print the System VM hypervisor backend
    abctl system backend hv   # switch to Hypervisor.framework (restarts the VM)
    abctl system backend vz   # switch to Virtualization.framework (default)

    abctl disk usage          # Docker data image usage
    abctl disk compact        # trim free blocks from the data image

    abctl boot status         # boot asset (kernel/rootfs) state
    abctl boot prefetch       # download boot assets ahead of first launch

    abctl info                # version, OS, arch, CPU count, machine count
    abctl version             # version only
    ```
  </Tab>
  <Tab>
    ```bash
    abctl machine create dev --distro ubuntu   # create a Linux machine
    abctl machine list                         # list machines
    abctl machine start dev
    abctl machine stop dev
    abctl machine remove dev

    abctl machine ssh dev                      # interactive shell
    abctl machine exec dev -- uname -a         # run one command
    abctl machine inspect dev                  # full configuration
    abctl machine info dev                     # guest system info
    ```
  </Tab>
  <Tab>
    ```bash
    abctl sandbox templates                     # list built-in rootfs templates
    abctl sandbox create --memory 512           # create a microVM sandbox
    abctl sandbox run <id> -- ./untrusted-bin   # run a command, stream output
    abctl sandbox exec -t <id> -- bash          # interactive session
    abctl sandbox cp ./file <id>:/workspace/    # copy files in or out
    abctl sandbox expose <id> 3000              # publish a sandbox port on the host

    abctl sandbox checkpoint <id> --name clean  # snapshot a booted sandbox
    abctl sandbox restore clean                 # boot a copy from the snapshot
    abctl sandbox list-snapshots

    abctl claude                                # Claude Code in its own sandbox
    ```
  </Tab>
  <Tab>
    ```bash
    abctl k8s start         # start the daemon-managed k3s cluster
    abctl k8s status        # cluster and host-integration state
    abctl k8s kubeconfig    # print the ArcBox-managed kubeconfig
    abctl k8s enable        # wire kubectl on the host to the cluster
    abctl k8s stop
    abctl k8s delete        # discard cluster state
    ```
  </Tab>
  <Tab>
    ```bash
    abctl doctor                    # run every runtime health check
    abctl top                       # live CPU/memory/network for the System VM
    abctl logs                      # daemon log, last 100 lines
    abctl logs -f -c dockerd        # follow the guest dockerd log
    abctl dns status                # DNS resolver for *.arcbox.local
    ```

    `abctl logs -c` accepts `daemon`, `helper`, `agent`, `dockerd`, and `containerd`.
  </Tab>
</Tabs>

Every command takes `--format json` for scripting, and `--debug` for verbose logging. Run `abctl --help` for the full tree.

## Migrating from another runtime

```bash
abctl migrate from docker-desktop
abctl migrate from orbstack
```

Both import containers, images, and volumes from the other runtime's data directory. Pass `--yes` to skip the confirmation prompt.

## CI usage

ArcBox's Docker socket is a standard Docker Engine API endpoint, so tools that expect a Docker daemon work unchanged — including local CI runners:

```bash
act -P ubuntu-latest=catthehacker/ubuntu:act-latest
```

## Socket paths

The daemon owns two sockets under `~/.arcbox/run/`:

| Socket | Purpose |
|--------|---------|
| `~/.arcbox/run/docker.sock` | Docker Engine API |
| `~/.arcbox/run/arcbox.sock` | ArcBox gRPC API |

The [privileged helper](./helper) also symlinks `/var/run/docker.sock` to the Docker socket, so tools that hardcode the standard path find it.

To point the Docker CLI at ArcBox without using a context:

```bash
export DOCKER_HOST=unix://$HOME/.arcbox/run/docker.sock
```
